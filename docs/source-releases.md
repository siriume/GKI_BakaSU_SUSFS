# 源码 Release 归档

## 分组和内容

每个 Android KMI / 内核系列使用一个预发布 Release，例如 `source-android13-5.15`、`source-android12-5.10`。这些 Release 不设为 latest，不影响正式内核发布。

归档在任何 BakaSU、SUSFS、功能补丁和 defconfig 修改前生成。默认保存 manifest 中全部项目的工作树及原配预编译工具链，排除 `.repo` 和原有 `.git`，另保留构建所需的轻量当前提交信息。符号链接和执行权限保留。额外下载的 LineageOS GCC 单独保存在 `source-toolchains`，以完整 commit 命名，不重复装进各个源码包。BakaSU/SUSFS 仍在解压后按构建选项拉取、集成。

## 命名和完整性

固定版本索引示例：

```text
source-android13-5.15
  android13-5.15.123-2023-11-r9-v1.json
  android13-5.15.123-2023-11-r9-v1-<源码摘要>-<上传标识>.tar.zst
```

单文件直接使用 `.tar.zst`；只有超过 2 GiB − 1 字节、实际产生多卷时，才使用 `.tar.zst.part0000`、`.part0001` 等后缀。LTS 索引包含完整源码摘要；其压缩文件名另含实际内核子版本，例如 `android13-5.15.220-lts-v1-...tar.zst`。JSON 保存实际内核版本、锁定 manifest、额外 GCC commit、源码摘要，以及各分卷的文件名、字节数和 SHA256。已有的单卷 `.part0000` 归档仍能正常恢复，无需重新上传。

每卷最大 2 GiB − 1 字节（2,147,483,647 字节）。恢复时按 JSON 中的顺序拼接，校验每卷大小和 SHA256，解压并恢复轻量提交信息后再逐个核对 Git HEAD。完整源码核对通过后才替换构建目录。固定版本还会检查 Makefile 子版本是否与输入一致。下载、认证和校验失败会明确报错，不会伪装成未命中然后全量拉取。

全部分卷上传成功后才上传 JSON 完成索引。并发上传使用不同的压缩文件名，完成索引只允许创建、禁止覆盖。同一归档并发上传时，后完成的任务复用先完成的索引，并删除本任务上传但未被该索引引用的重复附件。网络响应丢失时也会先检查索引，保留索引正在引用的包。中断上传留下的未引用分卷不会被读取。

手工解压时，请按 JSON 的 `parts` 顺序合并源码分卷，再解压到源码根目录；额外 GCC 分卷需另行合并并解压到该目录的 `gcc/`。无历史包还需调用 `scripts/source_git_seed.py` 的 `restore_seed_bundle(root)`，分别恢复源码根目录和 `gcc/` 中的当前提交信息。构建流程会自动完成这些操作。

## 更新规则

- 固定月份/revision：索引存在时直接复用，连首次归档锁定的辅助项目和 GCC 提交也一并固定，不再请求 Google 的 manifest。
- LTS：每次先解析当前 manifest 的全部项目和额外 GCC commit；只有完整提交组合发生变化才生成新的源码归档。历史包保留，文件内容不随 `lts` 名称改变。
- `cache_epoch`：构建与源码更新流程均默认为 `v1`。要重新解析并生成固定版本归档，可两边一起改成 `v2` 等新值。
- 内核构建：归档缺失时自动同步、验证、上传，然后继续打补丁和编译。
- 源码更新流程：归档存在时只检查完成索引，缺失时同步、验证和上传，不编译内核。

## 自动和手动运行

在 Actions 选择 **更新源码 Release**，可指定 `source_group`（如 `android13-5.15`）、`targets`（`configured` 或 `lts`）和 `cache_epoch`。`configured` 使用现有 JSON 与内核构建相同的子版本去重规则，不会枚举 JSON 外的上游分支，也不会修改版本选择。

默认分组选项为 `android12-5.10,android13-5.15`，同时更新这两组。可手动选择单组，或选择 `all` 更新全部分组。每天 UTC 19:00（北京时间次日 03:00）的定时检查，以及 **更新 GKI 版本数据** 工作流在 main 成功完成后的检查，也默认只处理这两组。首次检查会补齐所选配置中全部缺失归档，后续固定版本只读取索引，LTS 按提交变化更新。矩阵不额外限制并行数，实际并行数取决于 GitHub 可用 runner 和账号额度。

所选分组含 5.10 或 5.15 时，准备任务先统一解析两者共用的 LineageOS GCC 提交。该提交及所选历史格式的完整 GCC 归档已存在时，只核对索引和附件，不下载或重新打包 GCC；缺失时先生成一次，再启动源码矩阵。各任务使用准备阶段锁定的同一提交，源码归档缺失时从 Release 恢复 GCC 后同步内核及 manifest 项目。

所有源码 Release 均写入运行工作流的仓库，使用内置 `GITHUB_TOKEN` 的 `contents: write` 权限，无需额外 secret。分叉仓库会维护自己的源码 Release。

原先的 `source-v1-*` Actions cache 不再读写，已有条目可以手动删除或等待过期。ccache/Bazel、ThinLTO 及小型构建工具缓存沿用现有配置。

## 默认无历史与可选 Git 元数据

内核构建、定时更新和手动更新默认均使用无历史小包。归档排除 `.repo` 和原有 `.git` 文件、目录或符号链接；源码文件、预编译工具链文件、`.gitignore`、`.gitmodules`、执行权限和普通符号链接保留。额外 GCC 使用同样规则。

默认索引使用 `版本.json`，保留历史的索引使用 `版本-with-history.json`。归档中的 `.source-vcs` 保存当前 commit、目录树、指向当前提交的 tag 和 Git index，不保存源码 blob 或父提交。恢复时据此生成轻量 `.git`，供构建读取 HEAD、提交时间和版本信息；完整的锁定 manifest 仍保存在 JSON 索引里。

压缩包及 JSON 索引默认均不带 `no-history`；勾选保留历史后，两者均带 `with-history`。移除旧格式兼容和迁移逻辑，重新生成归档前需清理旧索引及旧附件。

需要原始 Git 元数据时，手动运行 **更新源码 Release** 并勾选 `include_history`（保留 Git 历史/完整元数据）。它保存同步时已有的浅克隆元数据，不会额外下载上游全部历史。轻量 `.git` 不适合 checkout、查看历史、完整内容 diff 或 fsck 等开发操作。

归档缺失时直接同步源码并生成所选格式，不再回退或迁移旧包。每个压缩分卷都严格小于 2 GiB，达到 2,147,483,647 字节即写入下一卷，最后一卷不足上限时按实际大小保存。

2026-10-14 本地对 Release 中 GCC `16f73337b3616cfe640b0130629a9569b30482ca` 做流式重打包测量：原包 472,670,223 字节（450.77 MiB），纯粹排除 Git 元数据后使用 zstd 1.5.7、级别 6 压缩为 241,255,513 字节（230.08 MiB），减少 48.96%。该测量未包含新版轻量提交信息；新版实际包会增加少量开销，源码包大小以实际上传结果为准。
